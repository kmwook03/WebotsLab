1. Webots가 Python 코드를 실행하는 원리

핵심부터 말하면 Python 파일을 Webots 월드 안에 삽입하는 것이 아니다. Webots 시뮬레이터와 Python 컨트롤러가 서로 다른 프로세스로 실행되고, Webots가 제공하는 Controller API를 통해 매 시뮬레이션 스텝마다 센서값과 액추에이터 명령을 교환한다.

1. 월드 열기worlds/amr_search_rescue.wbt를 읽고 Robot과 센서·모터 노드를 생성한다.
2. 이름 해석Robot의 controller "amr_search_rescue" 필드를 확인한다.
3. 프로세스 실행controllers/amr_search_rescue/amr_search_rescue.py를 설정된 Python으로 실행한다.
4. API 연결Robot()이 시뮬레이터와 연결되고 이름으로 장치 프록시를 얻는다.
5. 동기 반복robot.step(64)마다 물리 진행, 센서 수신, 판단, 모터 명령 전송을 반복한다.

1.1 이름이 연결 계약이다

월드의 Robot 노드에 적힌 controller 이름과 controllers 아래 폴더 이름이 같아야 한다. 이 프로젝트의 연결 관계는 다음과 같다. 

# worlds/amr_search_rescue.wbt
DEF AMR Robot {
  controller "amr_search_rescue"
  children [
    Lidar { name "LDS-01" }
    Camera { name "camera" }
    Gyro { name "gyro" }
    # motors, position sensors, display, emitter ...
  ]
}

# Webots가 찾는 컨트롤러 진입점
controllers/amr_search_rescue/amr_search_rescue.py

Python 코드의 getDevice("LDS-01")도 같은 원리다. 문자열이 월드의 장치 name과 정확히 일치할 때만 해당 장치의 Controller API 프록시를 얻는다.

1.2 controller 모듈은 Webots와 Python 사이의 다리다

from controller import Robot의 controller는 이 저장소의 모듈이 아니라 Webots가 제공하는 Python 바인딩이다. Webots는 컨트롤러를 실행할 때 이 모듈을 import할 수 있도록 실행 환경을 구성한다. Robot()은 일반 로봇용 연결을 만들며, 월드 전체 노드와 실제 좌표를 임의로 읽을 수 있는 Supervisor 권한은 갖지 않는다.

Webots 시뮬레이터가 담당Python 컨트롤러가 담당
월드 로딩, 강체 물리, 충돌, 렌더링센서값 해석, 지도작성, 경로계획, 미션 판단
카메라 영상과 LiDAR/자이로/엔코더 값 생성Controller API로 값을 읽어 일반 NumPy 데이터로 변환
모터 명령을 물리 모델에 적용좌우 바퀴 목표 각속도 계산 및 전송
시뮬레이션 시간과 64ms 스텝 관리robot.step()에서 다음 스텝까지 동기 대기

1.3 robot.step()이 만드는 폐루프

robot = Robot()
time_step = int(robot.getBasicTimeStep())  # 현재 월드는 64 ms

센서.enable(time_step)
모터.setPosition(float("inf"))             # 위치가 아닌 속도 제어 모드

while robot.step(time_step) != -1:
    센서값 = 엔코더 + 자이로 + LiDAR + 카메라
    상태 = 위치추정 + 지도 + 인식
    명령 = 미션판단 + 전역계획 + DWA + 안전검사
    모터.setVelocity(명령)
중요한 시간 개념: 컨트롤러가 현재 센서값으로 계산한 모터 명령은 다음 물리 스텝에 적용된다. 컨트롤러 계산이 끝나 robot.step()에 다시 도달해야 Webots도 다음 스텝으로 진행할 수 있다. 따라서 무한 루프, 매우 무거운 연산 또는 예외가 발생하면 시뮬레이션 진행도 함께 멈춘다.

별도의 mission_evaluator는 supervisor TRUE인 두 번째 Robot 컨트롤러다. AMR의 Emitter가 보낸 상태를 Receiver로 받고 실제 위치로 성공 여부만 채점한다. 이 통신은 AMR → evaluator 단방향이며 evaluator가 AMR에 정답 위치를 보내지는 않는다.

2. 전체 설계 개요

이 프로젝트는 센서, 상태추정, 지도작성, 인식, 임무판단, 경로계획, 안전제어를 분리한 계층형 구조다. Webots API에 직접 의존하는 부분은 메인 어댑터에 집중시키고, 나머지 알고리즘은 일반 데이터 구조와 NumPy 배열을 사용한다. 따라서 각 알고리즘을 Webots 없이 단위 테스트할 수 있고 다른 차동구동 로봇에도 비교적 쉽게 이식할 수 있다.

중요: 로봇 컨트롤러는 Webots의 실제 위치, 표적 위치 또는 객체 라벨을 읽지 않는다. Supervisor 기반 evaluator는 시험 결과만 관찰하고 로봇에는 정보를 보내지 않는다.

4. 알고리즘 계층별 동작

Webots 장치 초기화

모터를 속도 제어 모드로 전환하고 엔코더, 자이로, LiDAR, 카메라를 64ms 주기로 활성화한다.

필수 장치 이름: left/right wheel motor, left/right wheel sensor, gyro, LDS-01, camera.

로컬 좌표계 설정

시작 순간의 추정 자세를 (0, 0, 0)으로 저장한다. 월드에 배치된 실제 좌표와 무관하게 모든 지도, 표적 위치와 복귀 경로가 시작점 중심 좌표계에서 계산된다.

BOOTSTRAP 초기 스캔

선속도 0, 각속도 0.72rad/s로 제자리 회전한다. 누적 회전량이 5.9rad 이상이거나 11초가 지나면 EXPLORE 상태로 전환한다.

위치추정

엔코더 이동량으로 차동구동 오도메트리를 계산하고 바퀴 회전량 0.30, 자이로 회전량 0.70의 비중으로 융합한다.

distance = (left_distance + right_distance) / 2
rotation = (right_distance - left_distance) / axle_length

약 1.02초마다 LiDAR 점군을 기존 지도와 비교한다. 점수가 0.18 이상이고 오도메트리 예측보다 0.035 이상 개선될 때만 scan matching 보정을 수용하며, 보정 gain은 최대 0.12로 제한한다.

Occupancy Grid 지도작성

280×280 셀, 0.05m 해상도로 총 14×14m 지도를 구성한다. LiDAR 광선이 통과한 셀에는 free 증거를, 끝점에는 occupied 증거를 더한다. 확률은 log-odds로 누적하고 값은 일정 범위로 제한한다.

오래 다시 관측되지 않은 점유 증거는 감쇠해 움직이는 사람의 흔적이 영구 장애물로 남지 않게 한다. 경로계획 시 장애물은 기본 0.20m만큼 팽창한다.

Frontier 기반 미지 영역 탐색

free 셀이 unknown 셀과 맞닿아 있으면 frontier로 분류한다. 인접 frontier를 component로 묶고, 정보 획득량과 실제 A* 이동 비용을 함께 평가해 다음 탐색 목표를 선택한다. 

frontier score = information gain × weight - path cost × weight

A* 전역 경로계획

8방향 A*를 사용한다. 팽창 장애물과 unknown 셀은 통과하지 않고 대각선 corner cutting도 금지한다. 생성된 격자 경로는 line-of-sight 검사로 단순화한다.

RGB + LiDAR 표적 인식

카메라의 BGRA 픽셀에서 다음 조건으로 빨간 표적 후보를 추출한다.

red > 135
red > green × 1.55
red > blue × 1.55
red - green > 55

연결 성분의 중심으로 방위각을 구하고 알려진 표적 높이 0.60m로 단안 거리를 계산한다. 같은 방위의 LiDAR 거리와 일치할 때만 두 값을 융합해 주변 장애물을 표적으로 오인하는 현상을 줄인다.

접근 중인 미방문 표적과 방위가 연속되는 관측만 후보 갱신과 비주얼 서보에 사용한다. 표적이 보이는 동안에는 단안 거리의 큰 오차로 만든 전역 경로보다 거리와 방위각 기반 0.09~0.22m/s 비주얼 서보를 우선한다.

주행 가능 영역 segmentation + LiDAR 거리 연관

표적 탐지와 동일한 160×96 BGRA 프레임을 RGB로 변환한다. 영상 아래쪽 16%의 중앙값으로 현재 조명에서의 바닥 색·밝기 기준을 만들고, 수평선 아래 픽셀이 이 기준과 가까운지 검사한다. 각 영상 열은 아래에서 위로 추적하며 연속된 비바닥 영역을 만나는 순간 중단하므로, 장애물 뒤쪽 바닥이 보여도 장애물을 관통한 free-space로 해석하지 않는다. 

camera bearing = (0.5 - pixel_x / (width - 1)) × horizontal_FOV

visual confidence = bottom-connected floor pixels / pixels below horizon
associated range  = 20th percentile of LiDAR returns within ±2.5°

가로 4픽셀을 한 bin으로 묶어 방위별 confidence, lidar_ranges, lidar_hits를 가진 TraversabilityFrame을 만든다. 바닥 신뢰도가 낮아도 LiDAR hit가 없으면 약한 비용만 주고, 가까운 LiDAR hit가 같은 방향에서 확인될 때 DWA 비용을 강하게 한다.

비전 결과는 현재 점유지도나 Safety Guard의 hard obstacle을 직접 만들지 않는다. 색·그림자 오분류가 곧바로 급정지로 이어지지 않게 하고, 실제 충돌 금지 판단은 계속 360° LiDAR가 담당한다.

명시적 미션 상태기계

BOOTSTRAP → EXPLORE → TARGET_APPROACH → CONFIRM_TARGET
                         ↑                 │
                         └── 3개 완료 전 ──┘
          3개 완료 → RETURN_HOME → COMPLETE

표적이 연속 4프레임 이상 안정적으로 보이면 접근을 시작한다. 표적 거리 0.95m 부근에서 정지해 1.2초 동안 확인한다. 확인된 세계 위치와 현재 카메라 방위를 함께 비교해 같은 표적의 거리 오차를 새 표적으로 세지 않으며, 고유 표적 3개를 확인한 뒤에만 출발점으로 복귀한다. 움직이지 못하면 임시 RECOVERY 상태로 전환된다.

DWA 지역 경로계획

현재 속도와 가속도 제한 안에서 여러 선속도·각속도 조합을 만들고 각 후보 궤적을 1.35초간 예측한다. 연속 LiDAR 프레임의 compact cluster는 로봇 이동을 보정한 세계 좌표에서 연결하고 속도를 추정한다. 목적지 진전, heading, 정적 여유, 동적 예측 여유, 비전 주행 가능성, 경로 거리, 속도와 회전량을 함께 평가한다.

예측 궤적이 robot_radius + safety_margin 이내로 정적 장애물 또는 시간별 동적 장애물 예측 위치에 접근하거나 현재 속도로 제동할 수 없으면 해당 후보는 즉시 폐기된다. 카메라 시야 안에서는 후보 궤적의 진행 방위를 TraversabilityFrame과 비교해 비바닥 신뢰도가 높고 LiDAR가 가까운 물체를 확인한 방향에 soft penalty를 추가한다. 카메라 시야 밖 후보는 이 비용을 받지 않는다.

독립 안전검사와 모터 출력

DWA가 만든 명령도 마지막 안전 계층을 통과해야 한다. 전방 ±42°의 속도 비례 정지거리와 360° compact cluster의 상대 TTC를 함께 검사한다. 위험 시 정지·전후진·좌우 회전 후보를 동일한 예측기로 평가하고 실제 분리거리를 개선하는 명령만 선택한다. 

stopping distance = robot radius
                  + hard-stop distance
                  + forward speed × TTC horizon

위험 트랙은 ID로 유지하고 충분히 멀어진 뒤에도 짧은 release dwell을 적용해 방향 반전과 센서 가림에 의한 재출발 진동을 막는다. 3초간 적용된 제어 명령이 있었지만 3.5cm 미만으로 이동하면 recovery를 수행하며, recovery 명령도 최종 안전검사를 다시 통과한다.

7.2 센서

  • LiDAR 해상도, FOV, 최소·최대 거리와 정면 방향 확인
  • 카메라 FOV, 해상도, 전방 방향과 BGRA 포맷 확인
  • 지도가 좌우 반전되면 LiDAR 각도 배열의 부호 또는 센서 rotation 확인

7.3 지도

  • 경기장이 14×14m보다 크면 MapConfig.size 증가
  • 더 세밀한 지도가 필요하면 resolution 감소
  • resolution을 줄이면 A* 연산량과 메모리 사용량이 증가

7.4 카메라 인식

  • 표적 색이 다르면 RGB mask 변경
  • 표적 높이가 다르면 단안 거리식의 0.60m 변경
  • 0.5m, 1m, 2m에서 실제 거리와 target_range 비교
  • 오검출 시 색상 기준과 target_stable_frames 강화
  • 빈 바닥에서 visual_free_confidence가 높고 근접 장애물에서 낮아지는지 확인
  • 바닥 색이 달라지면 chromaticity_threshold와 intensity_threshold를 한 번에 하나씩 조정
  • 카메라–LiDAR 방향이 어긋나면 정면 물체에서 중앙 bin의 lidar_ranges가 맞는지 확인

8. 해커톤 현장 시험 순서

  1. 바퀴를 띄우고 좌우 모터의 부호와 회전 방향 확인
  2. 1m 직진 후 실제 거리와 추정거리 비교
  3. 제자리 360도 회전 후 실제 각도와 추정각 비교
  4. BOOTSTRAP만 실행해 표시 지도와 실제 벽 형상 비교
  5. 정적 장애물 앞에서 hard safety override 확인
  6. 표적만 놓고 target_confidence와 target_range 확인
  7. 빈 바닥·상자·사람을 차례로 카메라 앞에 놓고 vision=confidence/hits 변화 확인
  8. 좁은 통로에서 A* 경로와 DWA 궤적 시험
  9. 사람이 횡단할 때 정지 또는 회피 동작 확인
  10. 표적 도달 후 출발점 복귀 확인
  11. 시작 방향과 표적 위치를 바꿔 최소 5회 반복
실패하면 여러 파라미터를 동시에 수정하지 않는다. 위치추정 → 지도 → 인식 → 전역계획 → 지역제어 → 안전 순서로 한 계층씩 확인한다.

9. 증상별 빠른 대응

컨트롤러가 즉시 종료

NumPy 설치 여부와 getDevice() 장치 이름을 확인한다. Display나 Emitter가 없는지도 확인한다.

계속 제자리 회전

frontier가 생성되지 않거나 경로가 모두 막힌 상태다. LiDAR 방향, free threshold와 장애물 팽창 반경을 확인한다.

표적을 찾지 못함

카메라 방향과 BGRA 채널 순서, RGB threshold, 표적 픽셀 크기와 조명을 확인한다.

빨간 물체를 오검출

색상 비율 조건을 강화하고 최소 component 크기와 안정 프레임 수를 늘린다.

vision 신뢰도가 항상 1 또는 0

카메라가 바닥을 충분히 보는지 확인한다. 다음으로 하단 기준 영역의 장애물 가림, 수평선 비율, 색상·밝기 threshold를 점검한다.

비전과 LiDAR 장애물 방향이 다름

카메라와 LiDAR의 전방 축, rotation, FOV와 LiDAR 각도 배열 부호를 확인한다. 정면 상자 하나로 중앙 bin부터 맞춘다.

복귀 위치가 틀림

바퀴 반경과 축간거리부터 재보정한 뒤 scan matching 채택 횟수와 점수를 확인한다.

Recovery가 반복됨

통로가 팽창 장애물에 의해 막혔는지 확인하고 속도, inflation과 stuck 기준을 함께 검토한다.

10. 현재 구현의 한계와 확장 방향

  • RGB 주행 가능 영역은 현재 프레임 하단의 바닥색을 기준으로 한 규칙 기반 방식이며 그림자, 반사, 바닥 재질 급변에 취약할 수 있다.
  • 사람·벽·상자를 의미적으로 분류하지 않고 비바닥 영역과 LiDAR 동적 장애물로만 처리한다.
  • 카메라는 160×96 단안 RGB이므로 metric depth는 LiDAR 연관 없이 신뢰하지 않는다.
  • 표적 인식은 밝은 빨간색과 높이 0.60m라는 사전 특징에 맞춰져 있다.
  • 지도 크기는 고정이며 자동 확장되지 않는다.
  • 대규모 pose graph optimization과 loop closure는 포함하지 않는다.
  • Display와 Emitter가 없는 공식 로봇을 위한 선택적 장치 처리가 필요할 수 있다.

공식 월드나 Robot PROTO를 받은 뒤 가장 먼저 확인할 것은 장치 이름, 로봇 치수, 표적 특징, 경기장 크기, 바닥 시각 특성이다. 이를 확정한 후에 계획·안전 파라미터를 튜닝해야 한다.
